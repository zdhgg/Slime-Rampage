# 全游戏美术升级规划 V1

## 文档目的

本规划为《Slime Rampage》建立一套可分批实施的高细节厚涂幻想风美术升级方案。范围覆盖可玩史莱姆、普通敌人、精英敌人、章节与重要 Boss、武器、攻击特效、地图环境和 UI，同时保持现有战斗规则、碰撞尺寸、招式节奏、玩法分支和存档结构不变。

当前规划基于两层基线：远程 `main` 为 `947fdbc`，Boss 动画兼容接口位于当前分支提交 `a8829fe`。接口已经提供只读的 `attackMove` 与 `attackPresentation`，因此后续动作美术可以读取招式身份、表现阶段和进度，而不需要在渲染层重建战斗状态机。

本轮只交付规划、规格和样板验收标准，不生成正式游戏素材，不批量替换资源，不修改游戏代码。

## 现有素材与渲染盘点

### 主战场 Arena

- `GameEngine._renderArenaFrame` 采用背景离屏画布、环境层、实体层、前景遮挡、对白和暗角的固定顺序。世界坐标与屏幕坐标分离，摄像机滚动只改变整体平移。
- 游戏画布按设备像素比渲染，`devicePixelRatio` 上限为 2；世界尺寸至少为 2400×1800。任何新素材都必须在 DPR 1 的逻辑尺寸下仍可辨识。
- `AssetManager` 以离屏画布预渲染角色和特效。当前共生成 132 个精灵键：6 种史莱姆表情、3 个进化配件、3 个通用战斗特效、9 个普通敌人角色、3 个 Boss 角色；每个角色有 4 个行走帧和 1 个攻击帧，并同时保留普通与 `cyber_` 变体。
- `SlimeRenderer` 使用 `SlimeAppearance` 的路径、渐变和分层结构绘制史莱姆。6 个血统共享相同的逻辑锚点，战场半径通常约为 26px；选择页 `SlimePortrait.vue` 复用相同的外观数据。
- 普通敌人的逻辑半径约为 11–17px，渲染约为半径的 2.9 倍；精英通过金色标记和属性环与普通敌人区分。Boss 逻辑半径约为 34–40px，渲染约为半径的 2.6 倍。
- `WeaponVisuals` 以材质、形态、元素和等级组合生成弹体、拖尾与命中特效；当前已有基础、共生、火、水、毒、雷、酸、凝胶、爆裂、蒸汽、混沌等材质，不应在升级中重新发明一套会与战斗数据脱节的颜色系统。
- `MapDecor` 当前支持湿苔边境、腐化洞庭和王城废垒三类主战场主题，背景与前景均为程序化绘制；`AmbientLayer` 负责萤火、孢子、余烬等环境粒子。

### 章节 Boss 与重要 Boss

- 通用 Boss 目前按骑士、法师、弓手三种身体模板生成；12 名远征 Boss 复用这三类身体，招式、对白和机制不同，但外观区分度有限。
- 重要远征名单包括边防官、信标术士、猎团长、净巢司祭、王城盾将、王庭司库、灰烬圣骑、守陵王魂、封印主教、王座近卫、末代元帅和讨伐统帅。
- 当前角色帧仍由 `CyberCharacterArt` 与 `AssetManager._drawCharacterFrame` 程序化绘制，Boss 仅放大并增加王冠、光环、法阵或武器弧光。这是后续厚涂重制的主要断层来源。
- 当前边防官拥有独立追击、盾击、枪刺、冲锋、预警和收势表现；后续美术必须以现有 `attackPresentation` 的 `id`、`name`、`stage`、`progress`、`clock` 和 `attackRemaining` 为只读输入。

### Runner 与塔防

- Runner 使用独立的 `RunnerRenderer`，逻辑是三车道、深度缩放和道路预警。角色尺寸由 `baseUnit` 和深度共同决定，远处单位会缩小到很小的屏幕尺寸；现有背景装饰使用 Kenney CC0 资产和程序化后备绘制。
- Runner 当前有 3 条路线、11 类敌方/障碍实体、3 个基础武器核心、3 个二级元素、3 个模块、9 个融合武器和多个战术道具。迁移需要同时覆盖近景角色、远景轮廓、道路预警、武器弹体和路线装饰。
- 塔防使用独立 `TowerDefenseRenderer` 与相对坐标布局，支持横屏和竖屏；当前有 16 类敌人、10 类塔、6 类章节小 Boss、5 个章节主题和 99 个关卡。敌人主体由 `cyber_` 角色精灵或形状后备绘制，Boss 使用更大的同类精灵和更粗的血条。
- 塔防美术不能依赖固定像素位置。素材必须适应 `projectTowerDefensePoint` 的横竖屏投影、路径间距、建造位间距和触控选择范围。

## 视觉规范

### 总体方向

采用高细节厚涂幻想风，但把细节集中在轮廓、材质、受光面和关键装饰上。画面需要先在缩小和灰度下成立，再用色彩和笔触增加层次。避免把所有单位都做成同样亮、同样复杂或同样带光环的“精致贴纸”。

视觉主张是“深色巢域中的生物材质与王权遗物”：

- 轮廓使用清晰的深色边缘或暗部夹层，厚涂纹理不越过功能轮廓。
- 每个单位只保留一个主要识别材料：史莱姆是半透明黏液，普通敌人是磨损装备或异形组织，Boss 是可读的武器与装甲构造。
- 高光集中在眼睛、武器刃口、核心、护盾边缘和招式释放点；环境和 UI 的高光不能抢过玩家和预警。
- 背景使用低对比大色块、材质笔触和深浅分层；战斗对象使用更明确的轮廓与中高对比。
- 元素颜色继续服务既有战斗材质：火偏橙红、水偏青蓝、毒/酸偏黄绿、雷偏金白、虚空偏紫。相同颜色必须在玩家弹体、敌方预警、地图环境和 HUD 中保持语义一致。

### 视觉层级

| 层级 | 主要对象 | 识别手段 | 细节与亮度约束 |
| --- | --- | --- | --- |
| 玩家 | 六种史莱姆、伙伴 | 独特身体轮廓、眼神、血统配件、主色 | 轮廓和眼睛最稳定；常驻高光少，攻击时才提高亮度 |
| 普通敌人 | 9 类 Arena 敌人、Runner 普通敌人、塔防基础敌人 | 职业/行为轮廓、单一材质、武器方向 | 细节少而明确；同屏大量出现时仍能快速分组 |
| 精英 | 精英敌人、Runner 统领、塔防高阶敌 | 普通轮廓不变，加一处冠饰/核心/护甲和属性色 | 只增加一层信息，不靠满身发光与 Boss 竞争 |
| 小 Boss | 塔防章节小 Boss、Runner 破阵要塞等 | 更大体量、专属核心形状、机制相关装置 | 复杂度介于精英和章节 Boss 之间 |
| 重要 Boss | 12 名远征 Boss、通用和最终 Boss | 专属武器、装甲构造、头部标志、阶段变化 | 远看先识别武器和轮廓，近看再读材质与纹章 |
| 招式预警 | 扇形、冲锋线、环、方阵、弹道 | 形状、边缘、进度，不依赖单一色相 | 必须压过背景但不盖住玩家；优先使用轮廓、填充透明度和节奏 |
| UI | HUD、选择页、升级、塔防控制 | 版式、图标轮廓、文字和状态边界 | 控件和状态边界达到至少 3:1；正文文字达到至少 4.5:1。W3C 对非文字控件/图形提出 3:1，对普通文字提出 4.5:1 的最低对比参考。[WCAG 1.4.11](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html)、[WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |

### 屏幕尺寸与可读性

以 1280×720、1280×800、1024×768 和 390×844 为验收视口，分别在 DPR 1 和 DPR 2 检查。逻辑尺寸不能因高 DPI 而改变，细节只允许提升边缘质量。

- Arena 玩家与近身普通敌人必须在 32–52px 的常见屏幕体量下读出身体轮廓和攻击方向；敌人职业不依赖脸部细节识别。
- Elite 与小 Boss 必须在 48–76px 下仍能读出精英标记或机制核心。
- 重要 Boss 在 68–110px 下先读出武器类别和轮廓，再读出纹章、材质和阶段颜色。
- Runner 远处单位只保留轮廓、道路占位和威胁色，近处单位才显示武器细节；不得用缩放后不可见的细线传达危险。
- 塔防单位的主体、路径、建造位和预警范围必须在竖屏下不互相吞没；触控区域与绘制体量分离，不能为了可读性改变碰撞或建造逻辑。
- 灰度检查必须仍能区分玩家、普通敌人、精英、Boss 和预警；色盲检查必须能通过形状、纹理、边界或图标补足颜色语义。

| 普通敌人 | 1024×1024 透明源 | 2× atlas，单帧或 4–6 帧 | 4 走路帧 + 1–3 个行为帧；必要时镜像 | 9 个 Arena 类型优先保持职业共用骨架 |
| 精英 | 普通敌人源的变体层 + 独立核心/冠饰 | 与普通敌人同 atlas | 不新增完整骨架，优先复用轮廓和动作 | 精英差异集中在一处机制标志 |

| Boss 武器 | 1024×1024 透明源，独立 pivot 标注 | 与身体同 atlas 或独立武器层 | idle、windup、release、recover；支持镜像/旋转 | 不改变命中几何；表现锚点单独记录 |

### 武器、攻击特效与环境

- 武器弹体和命中特效使用 512×512 源、2×运行时导出；大范围环、冲锋轨迹、法阵使用 1024×1024 源。每个特效必须有中心点、旋转轴、有效可见边界和淡出建议。
- 预警图形优先用程序化几何加高质量材质贴图，而不是把攻击范围烘焙进角色图片。这样能继续保证范围、目标锁定和命中判定由战斗代码负责。
- 主战场环境按背景、可穿越中景、前景遮挡、环境粒子四层交付；每个主题先做一张可循环的材质板和 6–10 个高识别地标，再扩展装饰密度。
- Runner 环境按三条路线分别制作远景、道路材质、路旁地标、近景遮挡和危险预警；Kenney CC0 素材只能作为过渡或低关注装饰，不能直接与厚涂主体并列作为最终角色资产。[Canvas 重复绘制适合预渲染到离屏画布后复用](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)，因此重复环境纹理和静态装饰应优先做 atlas/离屏缓存。
- 塔防环境按五章主题制作低频大色块、道路边界、建造位平台、机关、章节 Boss 背景标志；不使用细小纹理弥补屏幕空间不足。

### UI 与肖像

- 角色肖像、Boss 头像、武器图标、元素图标和塔防图标统一制作 256×256 与 128×128 两档，保留透明边界和安全内边距。
- HUD 图标必须同时有轮廓和颜色语义；重要状态不依赖 emoji。文本层级、进度条和按钮状态沿用既有信息密度，不以装饰框增加阅读负担。
- UI 材质可使用厚涂金属、皮革、石板和黏液玻璃四种语义，但一个面板只选一种主材质。光晕只用于当前选中、危险、可施放和 Boss 阶段转折。

## 复用与重制边界

### 保留的技术与语义契约

- 保留所有实体 ID、Boss 类型、章节 Boss ID、武器 ID、元素材质 ID、地图主题 ID、Runner 类型和塔防类型。
- 保留逻辑锚点、碰撞半径、目标位置、预警几何、伤害时序、攻击冷却、移动速度、召唤数量、地图路径、建造位和触控范围。
- 保留 `AssetManager` 的同步后备绘制能力；正式素材加载失败时仍必须显示可玩、可识别的程序化版本。
- 保留 `SlimeAppearance` 的血统 ID、身体/面部层次和 `SlimeRenderer` 的逻辑半径，使选择页与战场不会出现两套血统造型。
- 保留 `WeaponVisuals` 的材质与形态 ID；升级只替换材质画面、轮廓和粒子，不把数值等级写进新的视觉状态机。
- 保留 Boss 动画兼容接口。渲染器只读 `attackMove` 和 `attackPresentation`，不得推进计时、移动实体、选择目标或结算伤害。

### 允许重制的表现层

- `CyberCharacterArt`、`AssetManager` 的角色帧、Boss 武器层、`SlimeRenderer` 的材质和面部细节、`WeaponVisuals` 的图形、`MapDecor`/`ChapterScenery`/`RunnerScenery`/`TowerDefenseScenery` 的绘制资源和 UI 视觉皮肤。
- 普通敌人可以在相同职业骨架上做厚涂材质重制；只有在轮廓足够稳定、行为仍可辨识时才允许换成新的身体比例。
- Boss 可以增加分层装甲、武器、纹章、阶段色和独立特效，但不将攻击范围画死在 PNG 内，不把新的位置变化写进渲染函数。

### 明确不迁移的内容

- 不迁移或整套恢复旧 `BossMelee` 及其他候选实现。
- 不导入会覆盖当前动画接口、旧工作区未提交资源或备份的整套美术包。
- 不用 Boss 精度标准强行放大普通敌人；普通敌人必须维持批量同屏时的轮廓和性能。
- 不通过美术替换修订净巢司祭、封印主教、讨伐统帅或其他 Boss 的实际伤害范围。

### 只读接口使用表

| 接口字段 | 美术用途 | 禁止行为 |
| --- | --- | --- |
| `attackMove.id` | 查找武器套件、招式图标、专属释放材质 | 不根据 ID 改攻击参数 |
| `attackMove.name` | HUD、对白旁的表现标题、样板标注 | 不在渲染器内维护第二份名称表 |
| `attackPresentation.stage` | 选择 pose、武器层、特效层和收势姿态 | 不在渲染器内推进状态 |
| `attackPresentation.progress` | 在预警/冲锋/收势间插值姿态、透明度和特效 | 不用它移动实体或改变命中 |
| `attackPresentation.clock` | 仅用于呼吸、材质闪烁和局部动画相位 | 不作为战斗时钟或目标选择依据 |
| `attackPresentation.attackRemaining` | 释放动作尾帧和残影强度 | 不重新结算一次伤害 |

普通 Boss、章节 Boss、边防官和未来 Boss 均应走同一表现适配器。没有专属素材时，适配器回退到职业家族默认帧；有专属素材时，只替换资源键和动作图层。

## 分批迁移顺序

每一批都必须包含玩家、普通敌人、精英或小 Boss、至少一种攻击特效和一段环境，避免先把 Boss 做到最终质量而让其他层级停留在旧风格。

### 批次 0：视觉圣经与样板板

交付一张可审阅的样板板：6 个史莱姆、9 个普通敌人、3 个精英变体、4 个近战 Boss、1 个远程/法师 Boss、3 种武器、4 种预警、1 个主战场主题、1 个 Runner 近景、1 个塔防章节小 Boss、1 个 HUD 状态组。样板板同时提供原尺寸、灰度、缩小和高对比截图。

### 批次 1：玩家与基础战斗语言

先完成 6 个史莱姆的身体、表情、血统配件、基础弹体和命中特效，再完成 9 个普通敌人的统一材质规范。这样可先锁定“黏液 vs 敌方装备/异形”的全局语言。

### 批次 2：精英与第一垂直切片

每个普通敌人类型制作一个精英变体，加入同一套精英冠饰、护盾、燃烧或召唤标志。选择第一章湿苔边境的一段主战场、一个章节小 Boss、一个主战场 Boss 和对应 UI，验证整屏层级。

### 批次 3：四名近战 Boss

按枪盾、塔盾短锤、双手战锤、长柄斧刃完成四名 Boss 的武器套件、动作关键帧和阶段材质。先完成边防官，以现有独立追击和连招作为接口验收样板，再扩展三名 Boss。

### 批次 4：全部重要 Boss 与章节 Boss

完成通用 Boss 三个家族、剩余远征 Boss、最终 Boss 和塔防章节 Boss。每名 Boss 至少有一处独占轮廓、武器或机制装置；共用基础骨架只用于降低生产成本，不得让 12 名远征 Boss 重新变成三张脸。

### 批次 5：武器、攻击特效和预警统一

把 Arena、Runner、塔防的弹体、命中、元素、范围预警和收势效果统一到同一材质词典。先做读得懂的形状，再加厚涂边缘、颗粒和光照，避免特效把角色和危险区域冲掉。

### 批次 6：地图环境

按主战场三主题、塔防五主题、Runner 三路线分别制作材质板、地标和前景遮挡。环境批次与角色批次交叉验收，确保同一色域下玩家和预警仍有足够对比。

### 批次 7：UI、肖像与全局收口

最后统一 HUD、Boss 轨道、技能卡、黑市、塔防面板、Runner 面板、选择页和结算页。UI 不重写信息架构，只升级材质、图标、状态边界和文字层级；完成后做全玩法截图和性能回归。

## 样板验收标准

### 视觉验收

- 同一张 1280×800 样板板同时展示玩家、普通敌人、精英、Boss、武器、预警、环境和 HUD；观看者在 3 秒内能指出玩家、精英、Boss 和当前危险区域。
- 灰度图仍能区分玩家/普通敌人/精英/Boss；四名近战 Boss 在缩小到约 70px 时仍能读出枪盾、塔盾短锤、双手战锤和长柄斧刃的轮廓差异。
- 普通敌人缩小到约 36–48px 时仍能按职业或行为分组；精英不靠仅改变色相来区分。
- Boss 细节集中在轮廓、武器、核心和阶段标志；同屏出现多个 Boss 时，轮廓和主色不会互相吞并。
- 主战场、Runner 和塔防各自截图中，预警比背景更清楚，但不遮挡玩家主体、路径或关键 UI。
- 颜色、纹理和形状三者至少有两种共同传达每个重要状态；危险、可施放、选中、冻结和低血量不能只靠颜色。

### 接口与行为验收

- 素材键与现有 ID 一一对应，缺失素材能回退到当前程序化绘制；不因素材加载失败阻塞开局。
- 渲染只读取 `attackPresentation`，不写回实体，不推进战斗计时，不选择目标，不改变位置，不结算伤害。
- `telegraph`、`dash`/`step`、`chain`、`recover`、`phase`、`dead` 各阶段都有明确 pose 或回退 pose；`progress` 为 0 和 1 时不存在跳帧或残影泄漏。
- 每段攻击的现有命中次数、伤害时序、预警形状和边界与美术替换前一致；边防官仍保持独立追击和连招。
- 15、30、60、120 FPS 下，动画采样只改变帧间平滑度，不改变状态结算和位置。

### 尺寸、性能与无障碍验收

- 视口：1280×720、1280×800、1024×768、390×844；DPR 1/2；横屏和竖屏塔防均通过。
- 角色、武器和预警的逻辑锚点、碰撞半径、范围边界和触控范围不变。
- 在既有压力场景下，静态素材应优先通过 atlas/离屏缓存复用；新增美术不得让 200 个 Arena 实体或塔防高密度波次的渲染帧时间增加超过 15%。重复图形适合预渲染到离屏画布后复用，这也是 Canvas 官方优化建议的方向。[MDN Canvas 优化](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)
- 主要 UI 文字目标至少 4.5:1；控件边界、选中/焦点状态和重要图形目标至少 3:1。细线不能作为唯一状态提示。
- 首次进入任一玩法时，素材加载失败、慢加载和缓存未命中都能显示当前后备图形；截图中不能出现空白角色、黑色贴图或错误图标。

### 内容与审核验收

- 每名重要 Boss 都有独占的武器/装甲/纹章/机制装置组合；共享骨架必须在样板对照中说明复用关系。
- 所有正式素材有来源、作者、许可和修改记录；Kenney CC0 资产继续保留许可证和来源说明。
- 不导入旧工作区的未提交 PNG 或候选 BossMelee 实现；新素材必须可单独回滚到当前程序化绘制。
- 每批次交付一张原尺寸对照、一张灰度对照、一段 60 FPS 实机录屏和一份资源键清单，审阅通过后才进入下一批。

## 需要确认的关键问题

1. 四名近战 Boss 的武器映射是否确认如下：边防官=枪盾、王城盾将=塔盾短锤、灰烬圣骑=双手战锤、王座近卫=长柄斧刃？讨伐统帅是否另定一套指挥型长柄武器/战旗，而不复用四者之一？
2. 正式素材源文件是否采用可编辑分层 PSD/KRA，运行时采用透明 PNG/WebP atlas？如果团队已有固定绘画软件、色彩空间或命名规范，请以现有规范替换本规划的建议值。
3. 首批样板是否需要同时包含 UI 重制，还是先锁定角色、武器、预警和环境后再做 UI？我建议样板包含最小 HUD 状态组，以尽早验证层级和对比度。
4. 是否接受“高细节只在近景/重要 Boss 集中，普通敌人以稳定轮廓和材质分组为主”的生产边界？如果所有普通敌人都要求 Boss 级细节，需重新评估 atlas 大小、制作周期和同屏性能预算。
5. 讨伐统帅、帝国双子元帅、灭绝机甲、Runner 破阵要塞和塔防 5 名章节 Boss 是否作为“最终 Boss”优先级处理，还是与 12 名远征 Boss 平行分批？
6. 是否把“厚涂幻想风”定义为偏暗背景、金色王权高光、饱和元素色的当前提案？若希望更明亮、偏童话或更写实，需要在样板板前先锁定方向。

## 通过确认后的第一阶段

收到关键问题确认后，第一阶段只做视觉圣经和样板板，不直接替换正式资源。样板板通过后，再按“玩家与普通敌人 → 精英和第一垂直切片 → 四名近战 Boss → 其余 Boss → 特效 → 环境 → UI”的顺序分批实施；每批都保留程序化后备、跑现有完整测试，并提交可审阅的截图和资源清单。
